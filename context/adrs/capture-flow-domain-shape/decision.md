## Context

`context/adrs/hexagonal-arch-shape/` and `context/adrs/backend-stack/` already settled the surrounding shape, and this decision builds on both rather than revising either: three non-overlapping layers with a transaction-agnostic domain, CQRS-lite (application-owned `UnitOfWork` commit boundary; queries read straight into DTOs without reconstructing aggregates), repository-style domain ports with an in-memory adapter first, and no command bus or mediator. `hexagonal-arch-shape` also left one thread open — "publishing to the outbox after a successful commit will need either per-handler duplication or introducing a bus later" — which this decision closes for the capture flow's single approval command, and for nothing else.

The scope is the aggregates behind capture: conversation → draft → approved note. Flashcard generation and the remember flow are separate, per `context/efforts/capture-flow/prd.md`'s Non-Goals.

The material comes from the duck session `context/duck-sessions/capture-flow-aggregates/`, which worked the aggregate shapes out in detail and closed by instructing that its own summary be re-verified against `context/efforts/capture-flow/{prd,stories}.md` rather than trusted. That re-verification found three gaps, and they are what this decision actually resolves:

1. **The duck session's `Note` had no topic at all.** AC-08 requires the draft note to carry "a topic, body, and tags", and AC-09 requires the draft's topic to be allowed to be *more specific* than the topic the user named at the start — so the note-level topic is a distinct fact from the session-level one, and neither can be dropped.
2. **A topic cannot be a plain string.** FR-009 (must-have) treats topics exactly like tags — "before proposing a new **topic** or tag, agent checks existing **topics**/tags for a close match and reuses it", echoed by AC-10. On top of that, the `overview-thougts` duck session settled that embeddings live at the level of a session's topic, and that flashcards link to each other transitively through that topic-embedding space. A bare string is not something a similarity search can reuse or an embedding can hang off.
3. **`Note.approve()` cannot write the outbox entry.** The duck session's summary has approval "trigger the outbox write", but `hexagonal-arch-shape` gives the domain zero imports from application or adapters and no notion of transactions or storage. The trigger point has to move out of the aggregate.

Two forces pull against each other throughout. Aggregate separation is cheap here because the `UnitOfWork` already provides cross-aggregate atomicity, so the usual "merge them to make the transition atomic" argument has no force in this codebase. Against that, the PRD's Non-Goals defer session persistence, listing, and resuming to a future effort, which removes the reader on the other side of most bookkeeping state — nothing in v1 ever loads back an abandoned session to ask what happened to it.

A prior, uncommitted draft of this ADR sat in this container and was reverted for settling four aggregates without a real pass over their operations. That draft is superseded by nothing formal — it was never recorded — and is simply replaced here.

## Decision

Five aggregates make up the capture-flow domain model. Each is an aggregate root with its own identity and its own repository port; cross-aggregate references are by id, never by held object.

**CaptureSession** — `id`, `topic: str`, `status` (`open` | `closed`), `created_at`.

- `start(topic: str) -> CaptureSession` — a class-level factory. It constructs the session, so it cannot be an instance method.
- `draft_note(topic: Topic, content: str, tags: list[Tag]) -> Note` — instance method, guarded on `status == open`. This is the entry point for note creation: the invariant "a note may only be drafted while the session is open" is knowledge only `CaptureSession` has, so it lives here rather than being duplicated at every call site of a bare `Note.draft(...)`.
- `approve(note: Note)` — instance method. Calls `note.approve(self.id)`, then `self.close()`. AC-15 makes approval and session end one act; expressing it as one domain method makes "approving always closes the session" a single assertion against a pure object, with no repositories, mocks, or `UnitOfWork` in the test.
- `close()` — guarded, one-way, invoked internally by `approve`.

`CaptureSession.topic` is the raw label the user names at AC-01. It is user input, not vocabulary — it deliberately does not participate in the reuse mechanism, because at session start there is nothing yet to reconcile against.

**Message** — `id`, `session_id`, `role` (`user` | `agent`), `content`, `created_at`. One class-level factory, `record(session_id, role, content)`, and no mutators: a message is immutable and append-only. `role` is a closed two-value set. Tool-call mechanics the agent runs while probing understanding (US-01) stay out of the domain model entirely; no story asks for them to be persisted.

`Message` carries no domain-computed sequence number — ordering is left to persistence (insertion order / `created_at`, tie-broken by an adapter-level surrogate key), so appending never requires knowing how many messages already exist. Assembling the full transcript for the next agent turn is a **query**, not a write-path concern: a dedicated query port reads a session's messages straight into DTOs, per `hexagonal-arch-shape`'s CQRS-lite split. Appends stay cheap regardless of transcript length, and the transcript is always one query away.

**Note** — `id`, `session_id`, `topic_id: UUID`, `content`, `tag_ids: list[UUID]`, `status` (`draft` | `approved` | `discarded`), `created_at`, `approved_at`.

- `draft(session_id, topic: Topic, content: str, tags: list[Tag]) -> Note` — class-level factory, called by `CaptureSession.draft_note()`.
- `update_content(content)`, `change_topic(topic: Topic)`, `add_tag(tag: Tag)`, `remove_tag(tag: Tag)` — instance methods, guarded on `status == draft`. The in-session redraft loop of US-06/AC-13 **mutates the single draft in place**; there is no version chain and no revert-to-previous, because no acceptance criterion asks for redraft history or an audit of the drafting process.
- `approve(session_id)` — instance method, one-way `draft → approved`. The `session_id` argument is a sanity check: it raises when it does not match `self.session_id`, catching wrong-aggregate mix-ups. It is explicitly **not** access control — any caller already holding `note.session_id` can bypass `CaptureSession` — and no capability or token scheme is introduced to make it one.

`Note` stays a separate aggregate root rather than a child entity of `CaptureSession`. The atomicity that would have motivated merging is already supplied by the `UnitOfWork` committing both saves in one transaction, and staying separate matches how `Message` already references `session_id` without being nested.

`Note.approve()` and the mutators stay **public**, with full domain vocabulary. Python has no real package-private enforcement — underscore prefixes are convention only — so an underscore would cost ubiquitous language and buy no enforcement. "Always go through `CaptureSession`" is a convention backed by tests and review, not a structural guarantee.

There is **no `abandon()` and no `discard()`**. Abandonment is a non-event at the domain layer: AC-07 ("no note or outbox entry") is satisfied by construction, since a draft that is never approved never produces an outbox entry regardless of its stored status, and the PRD's Non-Goals mean nothing in v1 reads an abandoned session's state back. `status: closed` on `CaptureSession` therefore means specifically "approved, note sent", not a generic terminal state. `Note.status` nevertheless keeps a third value, `discarded`, unreachable in v1 and retained as a forward-looking extension point.

**Topic** — `id`, `label`, `embedding`, `created_at`. One class-level factory, `mint(label, embedding)`, a thin construct-with-validation. This is the note-level, reconciled topic that AC-08 and AC-09 require, and the anchor `overview-thougts` designated for semantic linking. FR-008's "the session's topic label crystallizes over the course of the conversation" is realized as reconciliation happening at draft time, not at session start.

**Tag** — `id`, `label`, `embedding`, `created_at`. One class-level factory, `mint(label, embedding)`. No mutators.

**Vocabulary reconciliation lives outside the domain model.** For both `Topic` and `Tag`: an outbound port performs embedding-similarity search against existing rows, and an application service does the reuse-or-mint reconciliation — call the port per candidate label, reuse the existing row's identity on a match, else `mint(...)` on a miss. The aggregates never see candidate strings or similarity scores, only already-resolved objects. This is the same mechanism at redraft time (US-06) as at initial draft time; the only difference is when it fires.

**Operations take resolved objects; persisted state holds ids.** `draft_note(topic: Topic, ..., tags: list[Tag])`, `change_topic(tag: Topic)`, `add_tag(tag: Tag)`, `remove_tag(tag: Tag)` — so any invariant a `Topic` or `Tag` carries, including ones added later (a deprecated or merged state, say), is checked against the live object at call time. What `Note` *stores* is `topic_id` and `tag_ids`, extracted at the point of mutation, keeping storage normalized and the reference-by-id rule intact. When `Note` needs the full objects again, it reconstructs them lazily rather than eagerly hydrating on every load; the mechanism (injected loader, proxy, or otherwise) is left to `/plan`.

**The outbox envelope is written by the `ApproveNote` command handler**, inside the same `UnitOfWork` transaction as the `Note` and `CaptureSession` saves and before `commit()`. The handler calls `session.approve(note)`, persists both aggregates, constructs the envelope, and enqueues it through an outbox port. This is per-handler duplication rather than a domain event or a bus, consistent with `hexagonal-arch-shape`'s decided "no bus/mediator" stance — it closes that ADR's deferred outbox thread for this one command, not in general.

An already-approved `Note` cannot be un-approved or deleted. No story calls for retracting something already sent to the user's knowledge base, and nothing here is designed for it.

## Consequences

- Five repositories/ports exist for capture flow (`CaptureSession`, `Message`, `Note`, `Topic`, `Tag`) — two more than the flow's first sketch. Each is thin enough that `hexagonal-arch-shape`'s InMemoryFirst rule stays cheap to satisfy for all five.
- `Topic` and `Tag` are structurally identical — same fields, same `mint()` shape, same reconciliation mechanism, and two near-identical similarity-search ports. That duplication is accepted so that the 1-vs-N cardinality difference lives in the type rather than in a "which one is the topic" flag on a set-valued reference, and so that semantic linking has a distinguished anchor. If a third vocabulary ever appears, the right move is to factor a shared shape out; with two, factoring now would be premature.
- `CaptureSession` no longer guarantees message ordering or "no messages after close" by aggregate shape alone — both depend on the command handler checking status inside a shared `UnitOfWork`. A handler that checks status and then loses a race to a concurrent close is not structurally prevented. Accepted: this is a single-user tool with no concurrent-writer scenario in view.
- Message ordering is delegated to the persistence adapter. If a future adapter cannot guarantee stable insertion order — unlikely for the planned SQL adapter — this decision needs revisiting.
- `CaptureSession.approve(note)` mutates another aggregate root, which sits uneasily beside the decision to keep `Note` separate: the boundary that exists for persistence is deliberately crossed for behavior. Accepted in exchange for the invariant being provable in one mock-free assertion instead of depending on every caller remembering two steps.
- The "always approve through `CaptureSession`" rule has no structural enforcement — only the `session_id` sanity check, which catches mix-ups but not deliberate bypass. Tests and review are the whole mitigation.
- `Note.status` carries a value nothing can set. Every exhaustiveness check over the status — a match statement, a state-transition table, a test enumerating states — has a dead branch that cannot be exercised, and a reader has to be told that `discarded` is aspirational. Accepted as an explicit call against this session's own YAGNI recommendation.
- No `discard()` means an abandoned session leaves a `draft` note and an `open` session in storage indefinitely, with nothing that ever closes or purges them. Harmless while nothing reads them back, and it becomes real scope the moment the deferred session-listing effort lands: that effort will have to decide what an indefinitely-open session means before it can list one.
- Writing the outbox envelope directly in `ApproveNote`'s handler means every future command that must feed the outbox repeats the construction by hand. Accepted, deferred exactly as `hexagonal-arch-shape` already deferred it — a bus remains available later without this decision blocking it.
- Both vocabularies depend on embeddings existing and being queryable at draft time, which makes the embedding pipeline a hard prerequisite for the drafting step. No exact-match-only fallback is modeled for the case where embeddings are unavailable.
- Lazy reconstruction of `Topic`/`Tag` objects from stored ids is named but not designed. `/plan` inherits an unspecified mechanism, and a poor choice there (an N+1 on every note load, say) is a performance problem this decision does not guard against.

## Alternatives Considered

1. **Topic as a plain string on `CaptureSession` and `Note`.** The cheapest shape, and what the duck session's final summary implied. Rejected: FR-009 and AC-10 are must-have and require topics to be checked for close matches and reused, which needs a queryable, identity-bearing row with an embedding — and `overview-thougts` put the semantic-linking embedding on precisely this object. Choosing it would have meant recording a knowingly unrealized must-have requirement.
2. **Topic as a `Tag` in a distinguished role** — one vocabulary aggregate, with `Note.topic_id` pointing at a `Tag` and `tag_ids` at the rest. Genuinely tempting: fewer concepts, one similarity port, one table, and `overview-thougts` itself writes "topic/tag" as though they were one thing. Rejected because the PRD names them separately and gives them different jobs (FR-008 has the topic crystallize as the note's filing label; FR-010 has tags minted as facets), the cardinalities differ (exactly one vs. many), and "which of these tags is the topic" would become a convention enforced nowhere. Semantic linking also loses its distinguished anchor once topic is a role rather than a type.
3. **`Note` as a child entity inside `CaptureSession`'s aggregate boundary** — one repository, one atomic mutation, the factory method literally the only entry point for every note operation. Rejected: the partial-failure risk that motivates merging is already handled by the `UnitOfWork` committing both saves in one transaction, so the merge buys an atomicity guarantee that already exists, while costing the symmetry with `Message`, which likewise references `session_id` without nesting.
4. **`Message` as a child entity of `CaptureSession`** — the literal `Order`/`OrderLine` reading, giving free transactional ordering and a "closed session accepts no messages" guarantee at the aggregate boundary. Rejected: every append would require rehydrating the full message history, which is expensive exactly in the case this product cares about — a long think-out-loud conversation — for a guarantee that single-user scale does not need.
5. **Application-service orchestration instead of `CaptureSession.approve(note)`** — the handler calls `note.approve()` and then `session.close()` as two steps. Cleaner aggregate boundaries. Rejected: the AC-15 invariant would then live in every caller rather than in one place, and testing it would need repositories and a `UnitOfWork` instead of one assertion on a pure object.
6. **A domain event `NoteApproved`, raised by the aggregate and drained by the handler or the `UnitOfWork`** to write the outbox envelope. Cleaner separation than handler-side construction, and a natural extension point for future outbox producers. Rejected for now: it introduces event-collection and dispatch machinery for a single command, which is inconsistent with `hexagonal-arch-shape`'s deliberate deferral of a bus until a second case justifies it.
7. **Keeping `abandon()` and `discard()`** as the terminal counterpart to `approve()`, with `discard()` as a soft delete mirroring the accepted flashcard-rejection pattern. Rejected: it protects against nothing functional, since an unapproved draft already produces no outbox entry, and the PRD's Non-Goals mean nothing in v1 ever reads the resulting status back. A future reopen feature resumes a still-`open` session directly from storage; a future new-session action just calls `start()` again.
8. **A `Note` with no draft state at all**, existing only as already-approved-by-construction, with the pre-approval draft living as an application-layer DTO. Keeps `Note`'s invariants minimal. Rejected once the redraft loop was named: revising a draft under guards is exactly the stateful, rule-bound behavior domain objects hold, and moving it to a DTO relocates the guards without removing them.
9. **Bare ids in operation signatures** — `draft_note(content, tag_ids: list[UUID])`, `add_tag(tag_id: UUID)` — matching the reference-by-id convention everywhere. Was the initial resolution in the duck session. Rejected on the grounds that a `Topic` or `Tag` invariant can only be checked against a live object; the split adopted here keeps ids in storage while letting operations see the real thing.
10. **Non-public mutators on `Note`**, or a one-time capability token minted by `CaptureSession.approve()`, to make the session the only legal entry point. Rejected: Python offers no real enforcement for the first, and the second is more machinery than the risk warrants for a single-user tool.
11. **Append-only `Note` versions, one per redraft**, giving history and revert. Rejected: no acceptance criterion asks for redraft history, revert, or an audit trail of the drafting process.
12. **Retraction of an approved `Note`** (un-approve or delete after it has reached the knowledge base). Rejected for now, with no story calling for it; revisit if one appears.
