## Current State

Goal: refine the capture-flow domain model (aggregates + their operations) before re-attempting `/create-adr capture-flow-domain-shape`. The prior ADR attempt was reverted (two commits reset, files left unstaged on disk) for moving too fast — it settled four aggregates (`CaptureSession`, `Message`, `Note`, `Tag`) without a real pass on their operations, and without checking the settled `context/efforts/capture-flow/` PRD/stories first.

Reading `context/efforts/capture-flow/stories.md` surfaced US-03/AC-07 — "abandoning a session before approval results in no note or outbox entry being created" — which forced a re-check of the reverted ADR's `Note` shape. Resolved: the outbox is a separate channel (worker-to-worker communication feeding the actual Notion write), decoupled from the internal Notes table — so AC-07's "no note" is about what reaches the user's knowledge base, not about internal Postgres bookkeeping. `Note` is persisted for its whole lifecycle, three states: `draft → approved | discarded`. `discard()` is a soft-delete, mirroring the already-accepted flashcard-rejection pattern (kept as negative signal, not purged). Only `approve()` produces an outbox entry; `discard()` never does.

Also resolved: `Message.role` is a closed `user | agent` set — tool-call mechanics the agent runs while probing understanding (US-01) stay out of the domain model entirely, confirmed by the user.

`CaptureSession` needs a `topic` field, confirmed by AC-01 (session started by naming a topic) and AC-09 (the drafted note's topic can be more specific than the session's) — the reverted ADR's field list (`id`, `status`, `created_at`) was missing it.

User proposed `CaptureSession` as a factory method for `Note` (i.e. `session.draftNote(...)` rather than a bare `Note.draft(...)`). Re-reading stories.md surfaced two ACs that bear directly on this: AC-08 says the agent produces "a draft note" (singular) at the end of the conversation, and AC-15 says approval sends the note to the outbox "and the session ends" — approving the note must atomically close the session too. Combined with AC-07 (abandon ⇒ no note/outbox), both terminal transitions (`approve`, `abandon`) touch `CaptureSession` and `Note` state together, not just Note creation.

This whole thread is now resolved. **`Note` stays a separate aggregate root** (own identity, own repository) — the merge-into-CaptureSession option was dropped because the atomicity concern that motivated it is already handled by the Unit of Work committing both aggregate saves in one DB transaction, and staying separate matches the existing pattern where `Message` also references `session_id` without being nested inside `CaptureSession`. The factory-method idea itself survives independently: `CaptureSession.draft_note(content, tag_ids) -> Note` is the guarded entry point for creation (only while `status == open`). For the terminal transition, `CaptureSession.approve(note)` is a cross-aggregate domain method — chosen over application-service orchestration because the "approve always closes the session" rule becomes a single testable assertion on a pure domain object instead of depending on every caller remembering two separate steps.

A visibility question followed: should `Note.approve()` be non-public so `CaptureSession` is the only legal entry point? Resolved no — Python has no real package-private enforcement (underscore prefixes are convention only), so the method stays public with full domain vocabulary; the "always via CaptureSession" rule is enforced by tests/code review, not language mechanics. User then proposed passing `session_id` into `Note.approve(session_id)` as a guard — clarified and accepted as a **simple sanity-check** (raises if the passed `session_id` doesn't match `self.session_id`, catching wrong-aggregate mix-ups), explicitly **not** an access-control mechanism (a full capability/token scheme was considered and rejected as more machinery than wanted — "prosta walidacja").

Then a bigger simplification: **is `abandon()`/`discard()` needed at all?** Resolved no, and dropped entirely. AC-07 ("no note or outbox entry") is already satisfied by construction — a draft `Note` that's never approved never reaches the outbox regardless of its status. The capture-flow PRD's Non-Goals explicitly defer session persistence/listing/resuming to a future effort, so nothing in v1 reads back an abandoned session's state. `status: closed` on `CaptureSession` now specifically means "approved, note sent" — abandonment is just the absence of an `approve()` call, a non-event at the domain layer. This also made the earlier open question about "no trace" scope for `CaptureSession`/`Message` moot (nothing is ever purged on abandon, so there's no scope to vary). One consequence, decided explicitly by the user against this session's own YAGNI recommendation: `Note.status` keeps its third value `discarded` as a forward-looking extension point even though nothing sets it today.

A side question that came up while examining cardinality: how does the in-session redraft loop from US-06/AC-13 ("receive a redraft reflecting it") work mechanically — mutate the single draft `Note` row in place, or append a new `Note` version per redraft (history/versioning)? **Resolved: mutation in place.** No AC asks for redraft history, revert-to-previous-version, or audit of the drafting process — `update_content()`/`add_tag()`/`remove_tag()` on the single draft row, as already shaped, is sufficient.

All threads from the original "consolidate the full per-aggregate operation list" ask are now closed. `CaptureSession.start(topic)` confirmed as a class-level factory, not an instance method, symmetric with `Note.draft(...)`. Un-approving/deleting an already-approved `Note` is explicitly rejected for now (no story needs it). `Tag` dedup/reuse-vs-mint is confirmed to live outside the domain model entirely — an application service reconciles candidate labels against an outbound similarity-search port, reusing an existing `Tag` on a match or calling `Tag.mint(label, embedding)` on a miss; the aggregates never see raw candidates or scores, only resolved `Tag` objects.

Tag reference shape went through one more refinement after the operation list looked "complete": user pushed back on plain `tag_ids` in operation signatures, since `Tag` should be able to carry invariants (even potential future ones, e.g. a later deprecated/merged state) that only a live object — not a bare id — can be checked against. Landed on a split: **operation signatures take full `Tag` objects** (`CaptureSession.draft_note(content, tags: list[Tag])`, `Note.add_tag(tag: Tag)`, `Note.remove_tag(tag: Tag)`) so any Tag-side invariant is checked against the real object at call time, while **persisted state stays `Note.tag_ids: list[UUID]`** (ids extracted at the point of mutation) — keeping storage normalized and the cross-aggregate-reference-by-id convention intact. When `Note` needs full `Tag` objects again later, it reconstructs them lazily rather than eagerly hydrating on every load; the exact mechanism (injected loader, proxy, etc.) is left for `/plan`, not decided here.

Confirmed: the tag reuse-vs-mint reconciliation is the same mechanism at redraft time as at initial draft time — same port, same application service, just triggered mid-conversation instead of once-at-the-end. No open threads remain on the aggregate shapes themselves.

**Session closed.** User is moving to `/create-adr capture-flow-domain-shape` to synthesize this log into a concrete decision record. Everything below is the final settled shape this session produced — the ADR authoring should treat it as the source material, re-verifying against `context/efforts/capture-flow/{prd,stories}.md` rather than assuming this summary is itself authoritative on any point not already cited to an AC/FR above.

Aggregates, final shape from this session:

- **CaptureSession**: `id`, `topic`, `status` (`open`|`closed`), `created_at`. Ops: `start(topic)` (**class-level factory**, constructs a new session), `draft_note(content, tags: list[Tag]) -> Note` (instance method, guarded — session must be open), `approve(note)` (instance method, calls `note.approve(self.id)` then closes self), `close()` (guarded, one-way, invoked internally by approve). No `abandon()` — abandonment is a non-event at the domain layer.
- **Message**: `id`, `session_id`, `role` (`user`|`agent`), `content`, `created_at`. Op: `record(session_id, role, content)`. Immutable, no mutators.
- **Note**: `id`, `session_id`, `content`, `tag_ids: list[UUID]` (persisted; full `Tag` objects reconstructed lazily when needed), `status` (`draft`|`approved`|`discarded` — third value currently unreachable, kept for future use), `created_at`, `approved_at`. Ops: `draft(session_id, content, tags: list[Tag])` (**class-level factory**, called internally by `CaptureSession.draft_note()`), `update_content()`/`add_tag(tag: Tag)`/`remove_tag(tag: Tag)` (instance methods, draft-only guard, mutate in place — no versioning), `approve(session_id)` (instance method, draft→approved, validates `session_id` matches, triggers outbox write). No `discard()`. Own aggregate root, own repository — not nested inside `CaptureSession`. Public API, called by `CaptureSession`'s methods above; direct calls aren't structurally blocked, only discouraged by convention/tests.
- **Tag**: `id`, `label`, `embedding`, `created_at`. Op: `mint(label, embedding)` (**class-level factory**, thin construct-with-validation — dedup/reuse logic lives in an application service, not here). No mutators decided yet — the invariant-checking motivation above is about future-proofing, not a concrete mutator that exists today.
