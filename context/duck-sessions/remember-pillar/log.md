**Card content available to remember today** (`backend/src/domain/distill/card.py`): `id`, `note_id`, `front`, `back`, `anchor`, `discard`, `created_at`.

**Settled so far:**
- **`ReviewSession` is persistent and resumable from the first cut.** The TUI overlay makes leaving a review mid-way an expected gesture, so an ephemeral session would lose the user's place on the move the shell invites.
- **`py-fsrs` is wired as a real adapter immediately, with no in-memory fake.** `InMemoryFirst` keeps *infrastructure* out of the prototype; FSRS is pure in-process computation with no I/O, so a fake would stand in only for the arithmetic worth exercising for real.
- **The review log is the truth; algorithm state is derived.** Remember persists what stays true across any algorithm — `card_id`, `reviewed_at`, `grade` — because an adapter that owns its own persisted state *lies about being replaceable*: the port looks swappable while the state pins the algorithm in place.
- **The grade scale is a product decision** owned by the domain, independent of the algorithm. `distill-domain-shape` prohibits the algorithm's *state model* leaking up; a grade is the review's *input*, authored on the product side.
- **Derived state is memoized per card, stamped, and disposable.** Pure replay was rejected on its risks (below). A `ReviewItem` holds an indexable `due_at`, an opaque `scheduler_state` the domain never interprets, and a stamp naming the algorithm and its parameter version. It is a **cache of the log, never a second source of truth**, enforced by one invariant: *a `ReviewItem` must be deletable and fully reconstructible from `ReviewLog` without changing the schedule.* That invariant is directly testable, and failing it is the signal that the adapter started lying again.
- **`due_at` lives outside the opaque blob**, as a real domain field. "When next" is algorithm-neutral — every scheduler produces it — and keeping it outside is what restores an indexed queue query.
- **Fuzz stays on.** The user keeps FSRS's interval randomization as a genuine feature rather than trading it for determinism; the rebuild invariant is preserved by having the **log carry the randomization draw per review entry**, which is a fact about that review event rather than algorithm state.

- **`ReviewLog` is a typed event stream from day one, under a scoping rule.** The rule: *the log accepts exactly those events that change the derived schedule, and nothing else.* What forces the event shape is not append-only-ness but the reconstruction invariant — if suspend, postpone or reset ever exist and are absent from the log, replay produces a different schedule than the memoized state and the invariant breaks, so "grades only" is sound only if grades are forever the sole scheduling-affecting action. Adding a type later is additive; converting a flat grade table into a typed stream later is a migration.
- **The scoping rule is what keeps that safe.** Only schedule-affecting events are validated by the reconstruction invariant; anything else enters with no test holding it in shape and stays forever as dead weight in replay. It settles one thing immediately: **session lifecycle does not belong in `ReviewLog`** — "opened", "expired" change no card's schedule. A session id stays as *metadata on a review event*, never as an event of its own.
- v1 defines exactly one event type (`reviewed`), which is the same move as distill's `version` pinned at `1` — structure bought now, with no branch that cannot be exercised.

**Model as it now stands (three aggregates):**
- `ReviewLog` — append-only typed event stream, algorithm-neutral, the truth.
- `ReviewItem` — per card, memoized derivation: `due_at` + opaque `scheduler_state` + parameter stamp. Created lazily on first review, so absence still means "new card".
- `ReviewSession` — resumable queue + cursor.

**Risks that shaped the above** (raised in full this session): silent global reschedule on a parameter or library-version change; loss of an indexable due-date query; fuzz breaking replay determinism; the grade enum becoming permanently non-shrinkable because the log is append-only and forever; non-review events (suspend, postpone, reset) having nowhere to live; a bad `reviewed_at` corrupting everything downstream of it. Memoization plus the stamp answers the first three; the rest remain live.

- **Parameter optimization is parked for the prototype** — not on cost grounds but on delivery time. It is purely additive, and there is no review history worth fitting against until a body of cards exists. Fixed FSRS defaults for the first version.

**What the park collapses.** With parameters fixed, the only thing that can invalidate a memoized state in v1 is a library version bump, which the stamp catches. The staleness check therefore almost never fires — but it stays, because it is genuinely free: the rebuild-from-log path has to exist anyway to satisfy the reconstruction invariant's test, so the lazy check is a stamp comparison on top of machinery already built. Same move the user made in `distill-pillar` when they kept a note `version` field pinned at `1`: one field of insurance bought now rather than unpicked later — while adding no branch that cannot be exercised, which is what `distill-domain-shape` cut when it removed the dead `rejected` status.

- **A `ReviewSession` freezes its *membership*, not its order.** It holds a set of `card_id`s chosen at start; ordering is computed fresh at resume, and cards discarded in distill meanwhile are filtered out. "Resume" therefore means "finish this batch", which is the thing resumability was wanted for.

**Live tension — the session's progress may be derivable rather than stored.** If reviews are logged with the session that produced them, then "where am I" is a query over `ReviewLog` — the frozen set minus the cards already reviewed under this session id — and `ReviewSession` needs no cursor field at all. That is the same log-as-truth move already made for scheduler state, applied a second time. The complication is FSRS's learning phase: a card graded at the lowest rating is meant to come back *within the same sitting*, so "has a log entry for this session" is not the same as "done with it here", and the done-predicate needs a second clause.

- **There is no done-predicate: the session is a filter (option C)** — confirmed by the user a second time after the option was restated, so it stands on understanding rather than on silence. What comes next is always the earliest-due card *inside the frozen set*, and the session is finished when nothing in the set is due. Learning-phase resurfacing falls out for free, because the scheduler alone decides when a card comes back. Progress is therefore not stored and not even a concept the session owns — "you did 12 in this sitting" is a derived statistic over log events carrying this session id, a display fact rather than a control mechanism.
- **A batch policy counts distinct cards, not review events.** With learning steps a card can be graded three times in one sitting; "a batch of 20" is a promise about coverage, so the count is of cards that left the due set, not of gradings performed.
- **A broken anchor degrades provenance, never the card.** `distill-domain-shape`'s grounding invariant is a **generation-time** rule — a card cannot be *born* with an unresolvable anchor. Extending it to runtime would mean a note edit silently destroys a card that already carries review history, leaving log entries behind for a card that no longer exists. What a review shows is `front` and `back`, which are self-contained; the anchor serves the jump-to-source gesture, so when it fails the gesture is simply unavailable and the card stays reviewable.
- **Remember holds no opinion about anchors at all.** Resolution happens where the note is rendered, behind the same port that serves card content; remember stores nothing about anchor state. If a broken anchor should be surfaced for the user to judge, the route is distill's existing `user_audit` discard — the one write-back already defined — so no new boundary crossing is invented.
- **A card discarded in distill needs no cleanup in remember.** Candidates come from the port, so a vanished card simply stops being selected. Its `ReviewLog` entries stay, being history, and an orphaned `ReviewItem` is inert.

**Superseded — four shapes for the done-predicate, weighed before option C was taken:**
- **A — horizon predicate.** Done = has a log entry for this session *and* derived `due_at` lies beyond a session horizon. A card graded lowest gets a due time a minute out and so stays undone. Keeps the session stateless, but the horizon is an invented constant that puts scheduling policy inside session logic.
- **B — explicit re-queue.** The session holds a mutable ordered queue; grading pops, the lowest grade pushes back. Easy to explain and exactly controllable, but reintroduces stored order and a cursor, contradicting the membership-not-order decision, and duplicates a judgement the scheduler already makes.
- **C — no predicate at all.** The session is only a filter. What comes next is always the earliest-due card *within the frozen set*, and the session is finished when nothing in the set is due. Learning-phase resurfacing falls out for free because the scheduler alone decides it. This is A with the horizon fixed at *now*, minus the constant.
- **D — richer log outcome.** The log records an outcome (reviewed vs. graduated-this-sitting) rather than a bare grade. Solves it directly, but permanently widens an append-only-forever vocabulary — the risk already named about the grade enum being non-shrinkable.

Recommendation put to the user: **C**, because it needs no constant, no cursor and no new log vocabulary, and it leaves resurfacing entirely with the scheduler, consistent with every boundary decided so far. Its one real cost: "session complete" stops being a state and becomes a momentary condition — nothing in the set is due *right now* — which leaves open how a session ever reaches a terminal state so the resumable list does not grow without bound.

**Current thread — the predicate as a domain-owned completion policy.** The user proposed lifting the predicate out of the session entirely: the session holds a policy (a value object) and asks it, so the session itself does not know how, when, or whether it ends. Response: this is worth doing, but only under a reframe. As an abstraction over the four *technical* options it is speculative generality — A–D are one-time design choices that would never coexist, so nothing would ever be swapped. As **session mode**, however, the variants are real and product-visible: exhaust everything due, a fixed batch of N, a timebox. Those genuinely coexist, are chosen by the user per session, and are named in review vocabulary rather than algorithm vocabulary — the same test the grade scale had to pass.

Two things confirmed in its favour: the predicate is a **pure function** of the frozen set, `ReviewLog` and the clock, so it needs no port and no infrastructure — and it is pure *only because* `due_at` was kept outside the opaque blob as a real domain field, which is that decision paying off a second time. And the policy should be **frozen onto the session at start**, exactly like membership: a session resumed after the default changed must keep the rules it began under.

One thing it does **not** solve, and the user's framing risks hiding: a policy answers "is it done?", but something has to *ask*, and asking only happens when the session is opened. An abandoned session is never asked and so never becomes terminal. The unbounded resumable-list problem is untouched, and aging or an explicit close is still owed.

**Two policies, not one — selection and completion are different axes.** The user observed that the policy framing also unlocks "review only cards from this topic". That is true but belongs to a second axis: *selection* decides what fills the frozen set, *completion* decides when the set is finished, and they compose — "20 cards from topic X" is selection(topic X) × completion(batch of 20). Merging them into one value object would collapse two independent questions into one vocabulary. This also answers the earlier open question about what a session selects. It is not new ground either: `overview-thougts` described remember from the start as "a command that opens a review session with flashcards on a given topic".

**Not every pair composes.** A selection that ignores due-ness — cram everything under a topic before an exam — leaves the default completion policy ("exhaust everything due") finishing instantly, because nothing in the set is due. A selection axis that can ignore due-ness therefore forces at least one completion policy that is not due-based.

- **Remember reaches distill through a port it owns.** A review renders a card's `front` and `back`, which live only in distill, so the cross-pillar read exists the moment anything is shown on screen — topic-scoped selection introduces no new dependency. The port resolves a *scope* (topics, a note, everything) to candidate `card_id`s plus the content a review renders; remember's domain stays keyed by `card_id` and never learns what a topic is.
- **Topic resolution stays inside distill.** `Note` already carries `topic: TopicSnapshot {id, label}` (`backend/src/domain/distill/note.py:19`), delivered by the `note_approved` envelope, so the adapter resolves `topic_id → note_ids → card_ids` in one hop without touching capture. Topic identity is stable across pillars because capture minted the `TopicId` (`backend/src/domain/capture/topic.py`) and the snapshot preserved it.
- **Recognition and selection are separate steps.** Turning a user's words ("topics foo, bar") into `TopicId`s is fuzzy by nature and happens **once, in capture**, where `Topic.embedding` and `MatchCriteria.best_match` with its configured threshold already live (`backend/src/domain/capture/vocabulary.py`, `vocabulary_match_threshold`). The command then receives ids, and remember's port selects by id — exact by nature. A port taking free text or embeddings would push fuzziness onto every caller, including a TUI picker that already holds exact ids, and distill could not serve it anyway: `TopicSnapshot` carries `{id, label}` and no embedding, so the envelope brought the label, never the vector.
- **The topic query is a join, not a stored edge.** Distill holds `Note.topic: TopicSnapshot` and `Card.note_id` as two separate relations, so the adapter joins `topic_id → note_ids → card_ids` inside distill. A consequence worth keeping: if a note ever changed topic, its cards follow automatically, because no copied topic exists anywhere to drift.
- **A session's topics are optional command parameters, plural, frozen onto the session.** Absent means everything. Plural now rather than later: set membership instead of equality is a nearly free implementation difference, while widening a singular field afterwards breaks the command and API contract.
- **The topic picker is a distill-side query**, so the user chooses among topics actually backed by notes that reached distill, rather than among capture's topics — some of which have no material on the review side at all.
- **A selection resolving to an empty set refuses the session** rather than creating one that is immediately complete. An empty session is a junk row and a misleading state; refusal is the honest answer.

**Superseded thread — how remember resolves a topic.** The question looked like it might force a reversal of one of distill's deliberate boundaries. Working it through says otherwise, for a reason that reframes it entirely: **remember must read distill's cards regardless.** A review renders a card's front and back, and that content lives only in distill. So the cross-pillar read is not introduced by topic-scoped selection — it already exists, inescapably, the moment a review shows anything on screen. The open question is not *whether* remember reads from distill but what shape that read takes.

That collapses the denormalization option. Copying topic onto remember's records requires a record to copy it onto, and `ReviewItem` is created lazily on first review — so a card never yet reviewed would have no topic and could not be selected by one, which is precisely the card a topic review is for. Lazy wrapping and denormalized topic are incompatible, and rescuing denormalization would mean either undoing lazy wrapping or adding the card-generation envelope `distill-domain-shape` deliberately refused. Both reverse a decision to solve a problem that is already solved.

What is left, and is being recommended: **a port on remember's side** that resolves a *scope* — a topic, a note, everything — to candidate `card_id`s, plus the card content a review needs to render. Remember depends on an interface it owns, named in its own vocabulary, with an adapter reaching into distill behind it, so distill's model never appears in remember's domain and remember's domain still never learns what a topic *is*: it stays keyed by `card_id`, and the topic vocabulary lives in the selection policy and the port. Selection then composes as *candidates from the port* ∩ *remember's own schedule view*.

This also reads `distill-domain-shape` correctly rather than around it. That ADR constrained the **write** direction — remember's one write back is a rejection command — and said nothing about reads, because a write across a boundary is the dangerous direction. And the isolation argument that justified denormalized snapshots in `outbox-shared` does not transfer: a snapshot exists so an **asynchronous** consumer processing an event later does not depend on state at processing time. Remember is synchronous and in-process, and a topic query wants exactly the *current* state, which is the opposite requirement.

- **Sessions expire.** A frozen set chosen against a week-old picture is not worth resuming: cards may have been discarded in distill meanwhile, and expiry also bounds how long a frozen set can outlive an algorithm version change, tying back to the stamp decision. Expiry is evaluated **lazily, when a session is looked at** — derived from its start time and nothing else — so it needs no sweeper and no worker, the same shape as the staleness check.
- **The expiry horizon is a configured value, not a hard-coded one** — an environment setting in v1, per-user later. It fits an established pattern rather than adding a mechanism: `backend/src/config/settings.py` already carries domain tunables of exactly this kind (`vocabulary_match_threshold`, `card_front_max`, `card_back_max`) injected downward.
- **The completion policy is persisted on the session**, not merely frozen by convention — a stored field, so a resumed session carries the rules it began under across restarts.
- **The horizon is read live, while the completion policy stays frozen** — a deliberate asymmetry. The completion policy defines *what the batch is*, so changing it mid-flight would rewrite a contract already agreed to; the horizon changes only how long a session stays on offer, and a user shortening it almost certainly means it to apply to the sessions they already have.
- **Expiry destroys no work.** Every review already performed is in `ReviewLog` permanently and already counted toward scheduling; a session is only a convenience over derived state. This is the fourth application of the same pattern in this session — do not store what can be computed — and it is what makes sessions disposable by construction rather than by decision.

**Deliberately left to the effort's framing and planning** rather than settled here — the user drew the line at this point, judging the remaining questions to be sizing and product detail rather than domain shape:
1. What the grade values are called, in review vocabulary rather than FSRS's.
2. Which selection and completion policies exist in v1 beyond the defaults (exhaust-what-is-due, and everything).
3. What surfaces "you have cards due", given nothing pushes and remember has no worker.

**Also left standing, recorded but not driving:** whether capture's assignment threshold (`vocabulary_match_threshold`, tuned for precision) suits topic *search*, which wants recall; cleanup of expired session rows; and whether a card whose note changed enough to make its answer wrong can be detected at all — it cannot, and the existing `user_audit` discard is the whole of the answer.

### 2026-09-09 — completion-policy: the done-predicate becomes a domain-owned policy on the session — ACCEPTED
Why: the user proposed extracting the predicate as a value object the session delegates to, so the session does not know how or whether it ends, and acknowledged up front that this does not defer the decision — one concrete policy is still needed now. Accepted on a reframe rather than as stated: as a wrapper over options A–D it would be speculative generality, since those are one-time design choices that never coexist and nothing would ever be swapped. Its real justification is that the variants are **product-visible session modes** — exhaust everything due, a batch of N, a timebox — which do coexist, are chosen per session, and are named in review vocabulary, the same test the grade scale had to pass. Two supports: the predicate is a pure function of the frozen set, the log and the clock, so it needs no port — and it is pure only because `due_at` was kept outside the opaque blob, that decision paying off a second time. The policy is frozen onto the session at start, exactly as membership is, so a session resumed after the default changed keeps the rules it began under.
Consequence: option C becomes the default policy rather than the only one, and the four options collapse into how a given policy expresses itself. Explicitly **not** solved: a policy must be *asked*, and only opening a session asks it, so an abandoned session never becomes terminal — session aging or explicit close is still owed.

### 2026-09-09 — selection-policy: selection is a second axis beside completion, and they compose — ACCEPTED
Why: the user noted that the policy framing also unlocks topic-scoped review. Accepted, but separated: what fills the frozen set and when the set is finished are independent questions, and folding them into a single value object would force one vocabulary to answer both. As two axes they compose — "20 cards from topic X" is selection(topic) × completion(batch). This also settles the open question of what a session selects, and it restores an intent that was in the design from the beginning: `overview-thougts` already described remember as a command opening a review session with flashcards on a given topic.
Consequence: a selection that ignores due-ness (cramming a topic) makes the default completion policy finish instantly, so the axes are independent but not freely composable — at least one non-due-based completion policy is implied by any such selection.

### 2026-09-09 — topic-read-path: remember has no vocabulary for topic, and no settled way to get one — OPEN
Why: falls directly out of the accepted selection axis. Remember's model is keyed by `card_id`, and `Card` carries only `note_id`; topic lives on distill's note, where it arrived in the `note_approved` snapshot. So topic-scoped selection needs a cross-module read that `distill-domain-shape` never settled — it fixed the *write* direction (rejection as a `user_audit` command) and said nothing about reads. Two shapes named without argument yet: a distill query port resolving a topic to `card_id`s, which remember intersects with its own due-ness, or remember denormalizing topic onto its own records the way `outbox-shared` denormalized labels into the envelope to stop consumers reaching back into capture. The second echoes an already-accepted pattern in this codebase; the first is cheaper but puts a live dependency across the pillar boundary.

### 2026-09-09 — session-expiry: sessions expire, evaluated lazily on read — ACCEPTED
Why: the user judged expiry sensible on three grounds — cards can disappear from under a frozen set, expiry limits how long a set can outlive an algorithm version change, and nothing should be maintained forever. They flagged a UX cost and asked whether they were reading it wrong. Argued in response that the cost is smaller than it looks, and for a reason already bought: because the log is the truth, expiry destroys no work — every review performed is logged permanently and already counted toward scheduling, so what expires is only "the batch I committed to", and that batch was chosen against a picture now known to be stale. Restarting under the session's frozen selection policy yields a strictly better set, which makes the recovery gesture a single keystroke rather than a loss. The mechanism matches every other decision here: expiry is derived from the start time and evaluated when the session is looked at, so there is no sweeper and no worker.
Consequence: this resolves the terminal-state debt left open by the completion-policy decision, but only for the *visible* list — expired rows still accumulate in storage, which is a cleanup concern rather than a domain one and stays deferred.

### 2026-09-09 — expiry-horizon: what sets the expiry threshold — OPEN
Why: expiry reintroduces the invented-constant objection raised against completion option A. Argued that it is a different kind of constant — a product statement ("a review batch goes stale after a day") rather than scheduling policy smuggled into session logic — so a single fixed value named in domain terms is defensible for v1. A second shape was raised and not pursued: letting the completion policy express its own staleness, since a timebox is stale the moment it elapses while an exhaust-everything-due batch is stale within about a day. Elegant, but it couples two axes that were just deliberately separated.

### 2026-09-09 — expiry-horizon: a configured value, read live rather than frozen onto the session — ACCEPTED
Why: the user took the single constant but made it configurable — an environment variable in v1, per-user configuration later. No new mechanism is needed: `backend/src/config/settings.py` already holds domain tunables of the same kind and injects them downward, so the horizon is one more entry in an established pattern. Raised in response, and settled here, a question the hard-coded version did not have: a configurable value can change between a session's start and its resume. The completion policy is frozen because it defines what the batch *is*, and rewriting it mid-flight would change a contract already agreed to; the expiry horizon changes only how long a session stays on offer, so a user shortening it means it for the sessions they already have. The asymmetry is deliberate and recorded as such, because it otherwise reads as an inconsistency later.
Supersedes: 2026-09-09 expiry-horizon (OPEN).

### 2026-09-09 — completion-policy: the frozen policy is a persisted field on the session — ACCEPTED
Why: the user confirmed that freezing means storing — the completion policy is written to the database on the session record, not held only for the life of a process. This is what makes the earlier asymmetry real rather than nominal: the policy survives restarts with the session, while the expiry horizon is read from configuration at each look.

### 2026-09-09 — topic-read-path: remember reads distill through a port it owns; no denormalization — ACCEPTED
Why: the question looked like it might force a reversal of a distill boundary, and does not, because the dependency it worried about already exists: a review renders a card's `front` and `back`, which live only in distill, so remember reads across the pillar boundary the moment it displays anything. Topic-scoped selection adds no new coupling. Denormalization is not merely unnecessary but incompatible with an accepted decision — copying topic onto remember's records needs a record to copy onto, and `ReviewItem` is created lazily on first review, so a never-reviewed card would carry no topic and could not be selected by one, which is exactly the card a topic review is for. Rescuing it would mean undoing lazy wrapping or adding the card-generation envelope `distill-domain-shape` deliberately refused. The accepted shape is a port on remember's side resolving a scope to candidate `card_id`s and the content a review renders, with an adapter behind it reaching into distill: remember depends on an interface it owns, distill's model never enters remember's domain, and selection composes as candidates-from-port intersected with remember's own schedule view. This reads `distill-domain-shape` correctly rather than around it — that ADR constrained the *write* direction, reads being the safe one — and `outbox-shared`'s isolation argument does not transfer, since a snapshot protects an *asynchronous* consumer from state drift while a topic query wants precisely the current state.
Supersedes: 2026-09-09 topic-read-path (OPEN).
Consequence: verified in code that the hop stays inside distill — `Note` already carries `topic: TopicSnapshot {id, label}` from the `note_approved` envelope, so the adapter never touches capture, and `TopicId` minted in capture keeps topic identity single across all three pillars.

### 2026-09-09 — selection-params: topics are optional, plural command parameters frozen onto the session — ACCEPTED
Why: the user proposed carrying optional topic fields on the command so the TUI or API can scope a session, which is exactly the selection policy's parameters and needs no new concept. Plural was recommended and taken: set membership rather than equality is a nearly free implementation difference now, while widening a singular field later breaks the command and API contract. The parameters freeze onto the session with the rest of the selection policy, which is what lets a resumed session say what it was about and lets "start fresh with the same selection" mean something.

### 2026-09-09 — empty-selection: the topic picker is a distill query, and an empty selection refuses the session — ACCEPTED
Why: the user chose the distill-side query with their own reason — it guarantees the notes actually exist on the review side — where the argument put to them was the adjacent one, that capture's topic list includes topics no material has reached distill for. Both point the same way and it is the same port, not a new mechanism. On the empty case the user chose refusal over an immediately-complete session: an empty session is a junk row and a misleading state, and "nothing to review in that topic" is the honest answer to give at the command.

### 2026-09-09 — topic-recognition: fuzzy recognition in capture, exact selection in the port — ACCEPTED
Why: the user asked whether the port should match by embedding rather than id, motivated by plugging review into the existing conversational capture handler where a user says "start a session for topics foo, bar". Separated into two operations on different layers: recognition (words to `TopicId`s) is fuzzy and belongs where the vocabulary lives; selection (`TopicId` to `card_id`s) is exact. Putting embeddings behind the port would make every caller inherit fuzziness, including a TUI picker holding exact ids, and it is not even available there — verified that distill's `TopicSnapshot` carries `{id, label}` with no embedding, so the envelope brought the label and never the vector, and an embedding match would require a second cross-pillar read into capture, the pillar remember was just kept clear of. Capture already owns the machinery: `MatchCriteria.best_match` over `Topic | Tag` against a configured `vocabulary_match_threshold`. The routing is what `overview-thougts` already described — a general dispatcher with a capture path and a remember path — so the conversational entry and the picker converge on one command with one argument type.
Consequence: two distinct failures now exist at different places — "I cannot tell which topic you mean" during recognition, which a conversation resolves by asking and a picker cannot raise at all, and the already-accepted "nothing to review in that topic" refusal at the command. Also flagged, not decided: capture's threshold is tuned for *assignment*, which wants precision, while *search* wants recall, so reusing 0.85 in both roles may be wrong.

### 2026-09-09 — topic-card-binding: the topic query is a two-hop join inside distill — ACCEPTED
Why: recorded as a precision on the user's restatement, which described distill as holding the topic-to-card binding. It holds two separate relations instead — `Note.topic` and `Card.note_id` — so the adapter joins through the note rather than reading a stored edge. Worth stating explicitly because it is a dividend of refusing denormalization: with no copied topic anywhere, a note that changed topic would take its cards with it, with nothing left to drift.

### 2026-09-09 — log-vocabulary: ReviewLog is a typed event stream, scoped to schedule-affecting events — ACCEPTED
Why: the user chose the event stream, reasoning from the log being append-only and serving reconstruction. Recorded with a stronger argument, because that reasoning justifies the log existing rather than its being typed: the **reconstruction invariant** is what forces it. `ReviewItem` must be deletable and rebuildable from `ReviewLog` without changing the schedule, so any action that affects scheduling and is missing from the log breaks that invariant — which makes "grades only" defensible solely if grades are, forever, the only scheduling-affecting action. That is not an assumption worth signing. The cost asymmetry agrees: a new event type later is additive, while converting a flat grade table into a typed stream later is a migration.
Consequence and guard: this widens the already-named risk that an append-only-forever vocabulary can only grow — the grade enum's problem now applies to event types too, and a type introduced and abandoned must stay replayable indefinitely. The user accepted a scoping rule as the counterweight: **the log accepts exactly those events that change the derived schedule, and nothing else**, because only those are validated by the reconstruction invariant and anything else enters untested and stays forever. The rule immediately settles that session lifecycle events stay out of `ReviewLog` — a session id is metadata on a review event, never an event itself — and it eliminates completion-predicate option D, since "graduated this sitting" changes no schedule beyond what the grade already changed. v1 has exactly one type (`reviewed`).

### 2026-09-09 — session-progress: option C — the session is a filter, progress is derived, not stored — ACCEPTED
Why: taken after the log-vocabulary decision eliminated option D and the recommendation stood unchallenged. C needs no invented horizon constant, no cursor and no new log vocabulary, and it leaves resurfacing entirely with the scheduler, which is where every other boundary in this session put it. It is the fourth application of the same pattern — do not store what can be computed — after scheduler state, session disposability and expiry. Progress stops being something the session owns: "you did 12 in this sitting" is a derived statistic over log events carrying this session id, a display fact rather than a control mechanism.
Supersedes: 2026-09-09 session-progress (OPEN).
Consequence: a batch completion policy counts **distinct cards that left the due set**, not gradings performed, because learning steps can grade one card several times in a sitting and "a batch of 20" is a promise about coverage.

### 2026-09-09 — broken-anchor: a broken anchor degrades provenance, it does not kill the card — ACCEPTED
Why: `distill-domain-shape` makes an unresolvable anchor reject a card, and the question was what that means once a card already lives in a schedule. Resolved by reading that invariant at its actual altitude: it is a **generation-time** rule about what may be born, not a runtime rule about what may survive. Promoting it to runtime would let a note edit silently destroy a card that already carries review history, leaving `ReviewLog` entries behind for a card that no longer exists — an orphan the append-only log can never clean up. What a review shows is `front` and `back`, which are self-contained; the anchor serves the jump-to-source gesture, so a failed resolution removes an affordance rather than invalidating knowledge. Remember therefore holds no anchor state at all: resolution happens where the note is rendered, behind the same port that serves card content, and surfacing a broken anchor for the user to judge routes to distill's existing `user_audit` discard rather than inventing a boundary crossing. Noted as undecidable rather than deferred: a note edit that makes a card's *answer* wrong cannot be detected by any mechanism, and the audit discard is the whole of the answer.
Consequence: a card discarded in distill needs no cleanup on the remember side either — candidates come from the port, so it stops being selected, its log entries remain as history, and an orphaned `ReviewItem` is inert. This is v1 insurance rather than machinery: distill builds no note amendment today.
