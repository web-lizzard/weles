# Note Detail Implementation Plan

## Overview

Deliver slice S-04 of the `distill-flow` effort: users can open a note from the list and read its full content inside Weles (FR-011 / AC-11). This adds the single-aggregate read path the domain shape ADR left open — a `GetNote` query on the backend, a `GET /notes/{note_id}` route, and a TUI screen reachable from `NoteListOverlay` via arrow-key selection and Enter. Seeing the cards a note produced (AC-12) is out of scope here — it was split into its own roadmap slice, S-06 (`distill-flow-note-cards`), materialized as a sibling change during this plan's discovery, so this change's `GetNote` response carries no card data at all.

## Current State Analysis

- `Note` (`backend/src/domain/distill/note.py:16-25`) already carries every field a detail view needs: `topic` (`TopicSnapshot`: `id`, `label`), `content` (`NoteContent.value`), `tags` (`list[TagSnapshot]`), `distillation_status`, `approved_at`, `created_at`, `updated_at`. `approved_at` is a required `datetime`, never `None`.
- `NoteRepository.get(note_id: NoteId) -> Note | None` (`backend/src/domain/distill/ports.py`) already exists and is already used elsewhere (`approve_note.py`-style lookups) — no port change needed. `InMemoryNoteRepository.get()` (`backend/src/adapters/out/in_memory/distill/note_repository.py`) is a plain dict `.get()`.
- No single-aggregate detail query exists anywhere in the codebase yet. `application/distill/queries/list_notes.py` is the query-package shape to mirror (`Protocol` port + data-only `NoteListItemDTO`, no `UnitOfWork`, per `context/foundation/rules/cqrs-lite.md`); its DTO stays as-is, this plan adds a sibling file, not a change to it.
- `backend/src/adapters/http/notes.py` holds exactly one route, `GET /notes`, on a module-level `router = APIRouter()` already registered unconditionally in `main.py`. A second route on the same `router` needs no `main.py` change.
- `backend/src/adapters/http/errors.py`'s `EXCEPTION_STATUS_MAP` already maps `"note_not_found": 404` for **capture's** `NoteNotFoundError` (`backend/src/domain/capture/exceptions.py:68`). Per `context/foundation/rules/exceptions.md`, `CoreException` auto-derives `code` from the class name (strip trailing `Error`, snake_case) — a distill-context `DistillNoteNotFoundError` derives to `distill_note_not_found`, which does **not** collide with capture's `note_not_found`. `backend/tests/unit/test_http_error_mapping.py` walks every `CoreException` subclass and fails if any derived `code` is missing from the map — the new mapping entry must land in the same phase as the exception class.
- `backend/tests/integration/conftest.py`'s `notes_client` fixture already builds an `InMemoryDistillNoteRepository` + `InMemoryCardRepository` and overrides `get_list_notes_query`; it is the natural place to add a `get_note_query` override using the same `notes` repository instance.
- TUI: `tui/src/app.tsx` renders `<CaptureScreen />` and, when `useAppStore.isNotesOverlayOpen`, an absolutely-positioned `Box` holding `<NoteListOverlay />`; a single top-level `useInput` closes the overlay on ESC. `NoteListOverlay.tsx` renders rows (topic, status badge, card count) with **no selection state** — `grep` for `upArrow`/`downArrow`/`ArrowUp` across `tui/test/` finds nothing, so arrow-key navigation is new to this codebase.
- `tui/src/store/index.ts`'s `useAppStore` currently holds only `isNotesOverlayOpen` + `openNotes`/`closeNotes`. `tui/src/store/notes.ts`'s `useNotesStore` (`items`/`isLoading`/`error` + `fetchNotes`/`startPolling`/`stopPolling`) is the sibling pattern for a new `useNoteDetailStore`.
- `tui/src/api/notes.ts` has `listNotes()` only; `tui/src/api/client.ts` exports one shared typed `openapi-fetch` client. `tui/src/api/stream.ts`'s `approveNote()` is the closest precedent for a typed, path-parameterized `client.GET`/`POST` call with status-aware error handling (`response.status` inspected on failure).
- `tui/src/api/generated/schema.d.ts` has no `/notes/{note_id}` path yet — it is regenerated by `pnpm generate:api` (`tui/package.json:20`) against a **running** backend's `/openapi.json`. The TUI client phase for `getNote` therefore depends on this plan's backend route phase having been implemented and its Manual Verification step (`pnpm generate:api`) run first.
- No tabbed or multi-sub-view screen exists in the TUI yet, but this change doesn't need one: with cards excluded, `NoteDetailScreen` is a single content view, not a tab switcher.
- Uncommitted, pre-existing polish to `NoteListOverlay.tsx`/`app.tsx`/`CaptureScreen.tsx` (full-screen overlay shell, per-row status badges, "← ESC to go back" hint, capture input disabled while the overlay is open) is already in the working tree from an earlier, uncommitted session on S-03. This plan builds on that state as given — it is not part of this change's phases.

## Desired End State

`GET /notes/{note_id}` returns a `NoteDetailDTO` (topic, full content, tags, raw distillation status, timestamps — no card data) for a known note, and a `404` with `code: "distill_note_not_found"` for an unknown one. In the TUI, `NoteListOverlay` supports arrow-key row selection with the active row highlighted in blue; pressing Enter on a `ready` note opens `NoteDetailScreen`, showing its topic, tags, and full content; Enter on a `generating` or `failed` note is a no-op. ESC from the detail screen returns to the list (not to capture); ESC from the list closes the overlay entirely, exactly as before. If the note disappears between list and open (404), the detail screen closes and the list shows an inline error, reusing the list's existing error-banner affordance.

Verify: run the backend and the TUI; approve a note and wait for it to reach `ready`; type `/notes`; arrow down to the note; press Enter; confirm the full content, topic, and tags render; press ESC once (back to the list, selection preserved) and again (back to capture, capture state untouched).

### Key Discoveries:

- `backend/src/adapters/http/notes.py` is a single shared `router` — the new route is a second function in the same file, no `main.py` edit.
- `NoteRepository.get()` and the auto-derived exception `code` mechanism mean this query needs **no new domain port** and **no explicit `code` override** — only a new exception class and one new `EXCEPTION_STATUS_MAP` entry.
- Splitting cards out of this change (to `distill-flow-note-cards`, S-06) removes `CardRepository` from this query entirely — `GetNoteQueryPort`'s only dependency is `NoteRepository`.
- `NoteListOverlay` and `app.tsx` are both already covered by passing tests (`noteListOverlay.test.tsx`, `app.test.tsx`) — adding arrow/Enter/ESC behavior to them is a single TDD'able phase per file-pair, not a stub-then-behavior split, since no new exported symbol needs to exist before a test can import it.

## What We're NOT Doing

- Displaying cards, card counts, or any card data on the note detail screen — moved to `distill-flow-note-cards` (S-06). `GetNote`'s DTO has no `cards` field and its adapter never touches `CardRepository`.
- Card-to-anchor jump (S-05, FR-013) — depends on S-06 as well as this change.
- The one-time "cards ready" notification (FR-014) — deferred non-goal, unchanged from prior slices.
- A gesture or entry point from the note detail screen into a future cards view — that belongs to `distill-flow-note-cards`'s own plan.
- Opening a `generating` or `failed` note's detail view — Enter is a no-op until the note reaches `ready`; no new UI surface (toast, disabled-row styling) is added for this beyond the existing badge already shown in the list.
- Scrolling for long note content — content renders wrapped in the fixed-height overlay `Box`; content taller than the terminal clips, matching this prototype's existing no-scroll stance.
- Pagination, SQL/durable adapters, or any change to `Card`/`Note` domain models — in-memory only, read-only query.
- Whole-effort non-goals: spaced repetition, manual card removal, regeneration, note editing, external publishing, a rejected-proposals surface, semantic search, non-capture note origins.

## Implementation Approach

A backend-first vertical slice, each TDD'able unit split into a stubs-and-interfaces phase followed by a behavior phase:

1. **Backend read model** — `GetNoteQueryPort` + `NoteDetailDTO` (new `application/distill/queries/get_note.py`, mirroring `list_notes.py`'s shape) and an in-memory adapter reading `NoteRepository` only, raising a new `DistillNoteNotFoundError` when the note is absent.
2. **HTTP** — `GET /notes/{note_id}` as a second route on `notes.py`'s existing router, path param converted to `NoteId`, 404 propagated through the existing `CoreException` → `core_exception_handler` machinery with one new `EXCEPTION_STATUS_MAP` entry.
3. **TUI data layer** — typed `getNote()` client (mirroring `approveNote()`'s status-aware error handling) → a dedicated `useNoteDetailStore` whose failure path closes the detail view and surfaces the error on the existing note-list error banner, reusing that affordance instead of building a new one.
4. **TUI navigation state** — `useAppStore` gains `selectedIndex` (list cursor), `isDetailOpen`, `selectedNoteId`; `closeNotes` is extended to reset all three so reopening the overlay always starts clean.
5. **TUI screens** — `NoteDetailScreen` (new, single content view) → `NoteListOverlay` gains arrow-key selection (blue highlight, clamped to the live item count) and Enter-to-open gated on `distillationStatus === "ready"` → `app.tsx`'s ESC handler becomes a two-level pop (detail → list → capture) and conditionally renders `NoteDetailScreen` in place of `NoteListOverlay` while a note is open.

**Intent**: Register the new code so the exhaustiveness test and the route both resolve it to `404`.

**Contract**: `EXCEPTION_STATUS_MAP` gains `"distill_note_not_found": 404`.

#### 3. Query port and DTO

**File**: `backend/src/application/distill/queries/get_note.py` (new)

**Intent**: Mirror `list_notes.py`'s query-package shape for a single-aggregate read, with no card data.

**Contract**:
```python
class NoteDetailTopicDTO(BaseModel):
    id: UUID
    label: str

class NoteDetailTagDTO(BaseModel):
    id: UUID
    label: str

class NoteDetailDTO(BaseModel):
    note_id: UUID
    topic: NoteDetailTopicDTO
    content: str
    tags: list[NoteDetailTagDTO]
    distillation_status: str
    approved_at: datetime
    created_at: datetime
    updated_at: datetime

class GetNoteQueryPort(Protocol):
    async def get_note(self, note_id: NoteId) -> NoteDetailDTO: ...
```

#### 4. In-memory adapter skeleton

**File**: `backend/src/adapters/out/in_memory/distill/get_note_query.py` (new)

**Intent**: Materialize the concrete adapter class the behavior phase fills in.

**Contract**: `InMemoryGetNoteQueryAdapter(note_repository: NoteRepository)` implementing `GetNoteQueryPort`; `get_note()` unimplemented (`raise NotImplementedError`).
