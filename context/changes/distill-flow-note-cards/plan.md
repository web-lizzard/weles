# Note Cards View Implementation Plan

## Overview

Deliver AC-12 / FR-012: from an open note, the user can see the cards that note produced. The slice adds a card read path to the backend (`GET /notes/{note_id}/cards`) and a two-tab note view in the TUI — `Note` and `Cards` — with a card-detail body swap under the `Cards` tab.

This change was split out of S-04 (`distill-flow-note-detail`) so the note-detail screen stays scoped to note content only. `GetNote` carries no card data; the card read surface is its own query.

## Current State Analysis

The domain layer is complete for this slice. `Card` (`backend/src/domain/distill/card.py:15-22`) carries `id`, `note_id`, `front`, `back`, `anchor`, optional `discard` and `created_at`; a card is live iff `discard is None`. `CardRepository.list_by_note` (`backend/src/domain/distill/ports.py:16-19`) is implemented in memory (`backend/src/adapters/out/in_memory/distill/card_repository.py:13-16`) and wired in `backend/src/adapters/compose.py:91-94`, but is consumed only internally, by `list_notes_query` to compute `card_count`.

Missing on the backend: any `/cards` route, any card query port or DTO, and any HTTP integration coverage for cards.

Missing in the TUI: card OpenAPI types, a cards API module, a cards store, card screens, and the navigation state to reach them. `tui/src/app.tsx:49` supports exactly one conditional inside the overlay (`isDetailOpen ? NoteDetailScreen : NoteListOverlay`); this slice adds a tab dimension and a card-detail level beneath it.

### Key Discoveries:

- Every user-facing card read must filter `discard is None`, or fabricated cards surface (`context/adrs/distill-domain-shape/decision.md:124`). The filter pattern is established at `backend/src/adapters/out/in_memory/distill/list_notes_query.py:15-18`.
- A `ready` note with zero cards is a documented success case, not a failure (AC-04 / FR-005), so the read path must return an empty list rather than an error.
- `errors.py` already maps `distill_note_not_found` to 404 (`backend/src/adapters/http/errors.py:41`), so raising `DistillNoteNotFoundError` from the card query needs no new handler.
- Query handlers never receive a `UnitOfWork` and read directly into DTO shape (`context/foundation/rules/cqrs-lite.md`).
- The note-detail store is the fetch-on-navigate template: reset state, fetch, and on error close the view and surface the message through the notes banner (`tui/src/store/noteDetail.ts:15-32`).
- The TUI API client maps snake_case wire fields to camelCase domain types and raises status-aware errors (`tui/src/api/notes.ts:24-42`).
- `card_count` is already available client-side per note through `useNotesStore` items (`tui/src/api/notes.ts:55`), which is what gates the `Cards` tab.
- OpenAPI types are regenerated by `npm run generate:api` in `tui/`, against a running backend (`tui/package.json:20`).

## Desired End State

From the note list, pressing Enter on a `ready` note opens a note view with a `Note` / `Cards` tab strip. The active tab renders with a blue background and black text. `→` moves from `Note` to `Cards` when the note has at least one card and is inert when it has none; `←` moves back. Under `Cards`, a scrollable list shows each live card's front, back preview and anchor quote; Enter opens that card in full with the tab strip still pinned, and `←` returns to the list. `r` refetches the cards. ESC anywhere in the note view returns to the note list; ESC on the note list closes the overlay to the capture screen.

Verify by running the backend and TUI, approving a note, waiting for generation, opening it, and walking the tab strip both directions.

## What We're NOT Doing

- Card-to-anchor jump / fragment highlighting — that is S-05 (`distill-flow-card-anchor-jump`, AC-13 / FR-013).
- The one-time "cards ready" notification (FR-014).
- Manual card removal, card regeneration, note editing, spaced repetition.
- Surfacing discarded cards anywhere in a user-facing read.
- A `CardRepository.get` port or a `GetCardQueryPort` — card detail renders from the already-fetched list.
- Polling the cards view. Cards for a `ready` note are terminal; `r` covers on-demand refresh.
- A US-06 BDD feature file. No US-06 feature exists today, and authoring acceptance tests is `/bdd`'s job.
- Any change to S-04's ESC semantics or to `GetNote`.

## Implementation Approach

Six phases in three stubs-then-behavior pairs, moving outward from the domain: backend read path, then the TUI data layer, then the TUI navigation and screens. Each stubs phase materializes the exported symbols the following phase's tests import, so the behavior phase can be written test-first against a compiling surface.

The backend query follows the established CQRS-lite shape exactly: a `Protocol` port plus a pydantic DTO in `application/distill/queries/`, an in-memory adapter reading through `CardRepository`, and a route in the existing notes router. The TUI mirrors the note-detail slice: a typed API module, a Zustand store that fetches on navigate, and screens that read from both stores.

Navigation is modelled as a tab axis plus a depth axis inside the already-open note view. `useAppStore` gains an active-tab field and a selected-card field; `←`/`→` move along the tab axis, Enter/`←` move along the depth axis, and ESC keeps its existing pop-to-list meaning untouched.

## Critical Implementation Details

`←` is overloaded by design: inside card detail it pops to the card list, and on the `Cards` tab with no card open it switches to the `Note` tab. Card detail must therefore be checked before the tab switch in the same `useInput` handler, or the tab will flip out from under an open card.

## Phase 1: Backend card-read contracts

### Overview

Materialize the query port, the DTO, the in-memory adapter shell, the HTTP route and the composition wiring. No behavior.

### Changes Required:

#### 1. Card list query contract

**File**: `backend/src/application/distill/queries/list_cards_for_note.py`

**Intent**: Give the card read path an application-layer contract that mirrors `list_notes.py` and `get_note.py`, so adapters and the route can be written against it.

**Contract**: A `CardListItemDTO(BaseModel)` with `card_id: UUID`, `front: str`, `back: str`, `anchor_quote: str`, `created_at: datetime`, and a `ListCardsForNoteQueryPort(Protocol)` exposing `async def list_cards_for_note(self, note_id: NoteId) -> list[CardListItemDTO]: ...`.

#### 2. In-memory query adapter shell

**File**: `backend/src/adapters/out/in_memory/distill/list_cards_for_note_query.py`

**Intent**: Stand up the adapter class with its dependencies injected, so composition can wire it before behavior exists.

**Contract**: `InMemoryListCardsForNoteQueryAdapter.__init__(self, note_repository: NoteRepository, card_repository: CardRepository)` and an unimplemented `async def list_cards_for_note(self, note_id: NoteId) -> list[CardListItemDTO]`. Both repositories are needed: the note repository to decide 404, the card repository to read cards.

#### 3. HTTP route

**File**: `backend/src/adapters/http/notes.py`

**Intent**: Expose the card list nested under the note it belongs to, matching the selection-addressed navigation the product intent names.

**Contract**: `GET /notes/{note_id}/cards` returning `list[CardListItemDTO]`, taking the query port through `Depends(get_list_cards_for_note_query)` and converting the path `UUID` with `NoteId(value=note_id)`, exactly as `get_note` does.

#### 4. Composition wiring

**File**: `backend/src/adapters/compose.py`

**Intent**: Construct the adapter once at module scope and expose it through a provider, as every other query is.

**Contract**: A module-level `_list_cards_for_note_query` built from `_distill_note_repository` and `_distill_card_repository`, plus `def get_list_cards_for_note_query() -> ListCardsForNoteQueryPort`.

### Success Criteria:

#### Automated Verification:
- `cd backend && uv run pytest` passes (no new tests yet; nothing regresses)
- `cd backend && uv run ruff check src` and the project's type check pass

#### Manual Verification:
- `cd backend && uv run fastapi dev src/main.py` starts, and `curl -s localhost:8000/openapi.json | grep '/notes/{note_id}/cards'` shows the route registered

## Phase 2: Backend card-read behavior

### Overview

Implement the adapter: live cards only, oldest first, 404 for an unknown note. Cover the route with HTTP integration tests.

### Changes Required:

#### 1. Live-card read

**File**: `backend/src/adapters/out/in_memory/distill/list_cards_for_note_query.py`

**Intent**: Return exactly the cards a user is entitled to see for one note, in generation order.

**Contract**: `list_cards_for_note` raises `DistillNoteNotFoundError` when `note_repository.get(note_id)` is `None`; otherwise it maps `card_repository.list_by_note(note_id)` filtered to `card.discard is None` into `CardListItemDTO`, sorted by `created_at` ascending. `anchor_quote` comes from `card.anchor.quote`; `front` and `back` from `card.front.value` / `card.back.value`. A note with no live cards yields `[]`.

#### 2. HTTP integration coverage

**File**: `backend/tests/integration/test_notes_http.py`

**Intent**: Pin the route's status codes and payload shape at the boundary the TUI consumes.

**Contract**: Cases — a note with live cards returns 200 and the DTO fields in `created_at` order; a note whose only cards are discarded returns 200 and `[]`; a `ready` note that generated nothing returns 200 and `[]`; an unknown note id returns 404 through the existing `distill_note_not_found` mapping.

### Success Criteria:

#### Automated Verification:
- `cd backend && uv run pytest tests/integration/test_notes_http.py -v` passes
- `cd backend && uv run pytest` passes

#### Manual Verification:
- With the backend running and a generated note in hand, `curl -s localhost:8000/notes/<note-id>/cards | jq` shows only live cards, oldest first
- `curl -s -o /dev/null -w '%{http_code}' localhost:8000/notes/00000000-0000-0000-0000-000000000000/cards` prints `404`

## Phase 4: TUI card fetch behavior

### Overview

Implement the API mapping and the store's fetch, refresh and error paths.

### Changes Required:

#### 1. `listCards` implementation

**File**: `tui/src/api/cards.ts`

**Intent**: Call the route and hand back camelCase cards, with the same status-aware error vocabulary the notes client uses.

**Contract**: `client.GET("/notes/{note_id}/cards", { params: { path: { note_id: noteId } } })`; on `response.status === 404` throw `new Error("Note not found")`, on any other failure throw `new Error("Failed to load cards")`. Maps `card_id`/`anchor_quote`/`created_at` to `cardId`/`anchorQuote`/`createdAt`.

#### 2. `useCardsStore` implementation

**File**: `tui/src/store/cards.ts`

**Intent**: Fetch on navigate and support an on-demand refresh, surfacing failures the way note detail does.

**Contract**: `fetchCards(noteId)` resets to `{ cards: [], isLoading: true }`, then stores the result or, on error, clears loading, returns the user to the note list, and writes the message into `useNotesStore`'s `error` banner. `refresh()` re-runs the fetch for the currently selected note id without clearing the visible list.

#### 3. Tests

**File**: `tui/test/cards.test.ts`, `tui/test/cardsStore.test.ts`

**Intent**: Pin the mapping and the store transitions against a mocked API module, mirroring `notes.test.ts` and `noteDetailStore.test.ts`.

**Contract**: Cases — successful mapping of all five fields; 404 raises "Note not found"; other failures raise "Failed to load cards"; `fetchCards` success populates `cards` and clears `isLoading`; `fetchCards` failure clears loading, leaves the note view, and sets the notes banner; `refresh` re-fetches for the selected note.

### Success Criteria:

#### Automated Verification:
- `cd tui && npm test` passes, including the two new suites
- `cd tui && npm run build` passes

#### Manual Verification:
- None — this phase has no user-facing surface of its own; the screens in Phase 6 exercise it

## Phase 5: TUI navigation and screen stubs

### Overview

Extend the app store with the tab and card-selection state, and stand up the tab strip and the two card screens as renderable shells.

### Changes Required:

#### 1. Navigation state

**File**: `tui/src/store/index.ts`

**Intent**: Give the note view a tab axis and a card-depth axis without disturbing the existing overlay/detail fields.

**Contract**: `AppState` gains `activeNoteTab: "note" | "cards"` and `selectedCardId: string | null`; `AppActions` gains `setActiveNoteTab(tab)`, `openCard(cardId)` and `closeCard()`. `openDetail` resets both new fields to their defaults (`"note"`, `null`), and `closeDetail` / `closeNotes` clear them.

#### 2. Tab strip

**File**: `tui/src/components/NoteTabStrip.tsx`

**Intent**: Render the `Note` / `Cards` header shared by every view inside an open note.

**Contract**: `NoteTabStrip({ activeTab, cardCount }: { activeTab: "note" | "cards"; cardCount: number })`. The active tab renders with `backgroundColor="blue"` and `color="black"`; the inactive one renders dim. Presentational only — no input handling.

#### 3. Card screens

**File**: `tui/src/screens/CardListScreen.tsx`, `tui/src/screens/CardDetailScreen.tsx`

**Intent**: Materialize the two card bodies so Phase 6 can drive them.

**Contract**: Both are zero-prop default exports reading from `useCardsStore` and `useAppStore`. `CardListScreen` renders rows and holds the list's `useInput`; `CardDetailScreen` renders the card matching `selectedCardId`. Bodies render placeholder structure only — no key handling, no selection logic.

## Phase 6: TUI navigation behavior and card screens

### Overview

Wire the tab axis, the card-detail depth, the refresh key and the routing, and cover it all with screen and store tests.

### Changes Required:

#### 1. Tab entry from the note

**File**: `tui/src/screens/NoteDetailScreen.tsx`

**Intent**: Let `→` cross into the cards tab, and only when there is something to see.

**Contract**: Renders `NoteTabStrip` above the existing note body. A `useInput` handler moves to the `cards` tab on `key.rightArrow` when the note's `cardCount` — read from `useNotesStore` items by `selectedNoteId` — is greater than zero, and does nothing when it is zero. ESC handling stays in `app.tsx`, untouched.

#### 2. Card list behavior

**File**: `tui/src/screens/CardListScreen.tsx`

**Intent**: Browse the note's cards and open one.

**Contract**: Fetches through `useCardsStore.fetchCards(selectedNoteId)` in a mount `useEffect`, as `NoteDetailScreen` does. Renders `NoteTabStrip` with `cards` active, then one row per card showing front, a back preview and the anchor quote, with the selected row in blue. `useInput`: `↑`/`↓` move selection with clamping; Enter calls `openCard`; `←` returns to the `note` tab; `r` calls `refresh()`. Renders a "No cards for this note" line when the list is empty.

#### 3. Card detail behavior

**File**: `tui/src/screens/CardDetailScreen.tsx`

**Intent**: Read one card in full without losing the tab context.

**Contract**: Renders `NoteTabStrip` (cards active) above the card matching `selectedCardId` — front, back and anchor quote, wrapped. `useInput` on `key.leftArrow` calls `closeCard()`.

#### 4. Routing

**File**: `tui/src/app.tsx`

**Intent**: Select the right body for the current tab and depth.

**Contract**: Inside the open overlay, when `isDetailOpen` is false render `NoteListOverlay`; otherwise render `CardDetailScreen` when `selectedCardId !== null`, else `CardListScreen` when `activeNoteTab === "cards"`, else `NoteDetailScreen`. The existing ESC handler is unchanged: ESC with the detail open returns to the note list regardless of tab or card depth; ESC on the list closes the overlay.

#### 5. Tests

**File**: `tui/test/cardListScreen.test.tsx`, `tui/test/cardDetailScreen.test.tsx`, `tui/test/noteTabNavigation.test.tsx`

**Intent**: Pin the navigation contract and the rendered surfaces, following the seed-Zustand-state and mock-the-API-module conventions in `noteDetailScreen.test.tsx`.

**Contract**: Cases — `→` on note detail with `cardCount > 0` activates the cards tab; `→` with `cardCount === 0` leaves the tab unchanged; `←` on the cards tab returns to the note tab; `↑`/`↓` move and clamp selection; Enter opens card detail and the tab strip is still rendered; `←` in card detail returns to the list, not to the note tab; `r` triggers `refresh`; the empty list renders the no-cards line; the active tab renders with a blue background; ESC from the cards tab and from card detail both return to the note list.

## Testing Strategy

### Unit Tests:
Card DTO mapping and the live/ordering filter in the in-memory adapter (pytest). TUI API mapping, store transitions, navigation-state reducers (vitest).

### Integration Tests:
`GET /notes/{note_id}/cards` through the FastAPI test client in `backend/tests/integration/test_notes_http.py` — 200 with cards, 200 with `[]` for both the no-cards and all-discarded shapes, 404 for an unknown note.

### Manual Testing Steps:
Run backend and TUI together, approve a note, wait for generation, and walk the full tab and depth axes in both directions, including the zero-card note.

## Performance Considerations

`list_by_note` is an in-memory scan over all cards; card volumes per note are small and the store is in-memory-first, so no indexing is warranted here. The cards view fetches once on open rather than polling, so an open view costs nothing while idle.

## Migration Notes

None. The change is purely additive: a new route, new TUI modules, and new fields on `useAppStore` with defaults that leave existing behavior identical.
